# Platform engineering design

FlashQuest is a learning product, but the repository is intentionally operated like a small production service. The goal is to make local development easy while keeping the runtime contracts clear enough for CI, containers, and hosted environments.

## Runtime topology

```text
browser
  |
  v
React/Vite SPA -> FastAPI API -> PostgreSQL
                     |
                     +-> Alembic migrations
```

Local Docker Compose starts the same three service boundaries used by the deployed architecture: web, API, and database.

## Health model

FlashQuest separates **liveness** from **readiness**:

- `GET /health` remains a backwards-compatible lightweight liveness endpoint.
- `GET /health/live` proves the API process is serving requests and returns service/version/environment metadata.
- `GET /health/ready` executes `SELECT 1` through the configured database session. It returns HTTP 503 when the database dependency is unavailable.

Docker Compose gates the web service on API readiness rather than merely checking whether the API process exists.

## Request observability

Every HTTP response includes:

- `X-Request-ID` — propagated from the inbound request when provided, otherwise generated by the API.
- `X-Response-Time-Ms` — server-side request duration.

Those headers make it possible to correlate a browser or proxy request with downstream logs without coupling the application to a specific observability vendor.

## Configuration contract

Runtime configuration is environment-driven:

| Variable | Purpose |
| --- | --- |
| `DATABASE_URL` | PostgreSQL/SQLAlchemy connection string |
| `APP_ENV` | Runtime environment label |
| `APP_VERSION` | Service version surfaced by API metadata |
| `LOG_LEVEL` | Reserved application logging level |
| `ALLOWED_ORIGINS` | JSON array or comma-separated browser origins |
| `VITE_API_URL` | API endpoint embedded into the frontend build |

No environment-specific credentials belong in the repository.

## Container posture

The API image:

- uses a slim Python runtime;
- installs only the OS package required for health probes;
- runs the application as an unprivileged `app` user;
- exposes a Docker health check backed by `/health/ready`.

The frontend uses a multi-stage Node build and serves static assets with Nginx.

## CI quality gates

The pull-request pipeline is deliberately read-only. CI does not rewrite or push contributor code.

A change must pass:

1. **Backend matrix** — Python 3.11 and 3.12 compilation, pytest, Ruff, and Black checks.
2. **Frontend** — npm clean install, ESLint, TypeScript compilation, and Vite production build.
3. **Migration smoke test** — PostgreSQL 16 starts as a service and Alembic upgrades a clean database to `head`.
4. **Container build** — Compose configuration is validated and both API and web images are built.

Documentation deployment remains a separate workflow so application CI and docs publishing have independent failure boundaries.

## Data and failure boundaries

- Alembic owns schema changes; application startup does not silently create or mutate tables.
- A healthy API process can still be **not ready** when PostgreSQL is unavailable.
- The study engine stores review events separately from current card state, preserving an audit trail for future analytics.
- The frontend's game XP/combo counters are intentionally session-local presentation state. Durable study mastery always comes from backend spaced-repetition state.

## Platform interview talking points

This project can be used to discuss:

- liveness versus readiness;
- dependency-aware startup ordering;
- immutable application builds and environment-driven configuration;
- migration validation before deployment;
- read-only CI quality gates;
- request correlation and latency metadata;
- container least privilege;
- maintaining product UX state separately from durable domain state.
