# Platform Engineering architecture 🏗️

FlashQuest’s is a learning product, but the repository is intentionally operated like a small production service. The architecture is designed to make local development simple while preserving the contracts Platform Engineers care about: **health, configuration, schema lifecycle, container posture, dependency ordering, CI quality gates, and observable failure boundaries**.

## Design goals

<div class="fq-grid" markdown>

<div class="fq-card" markdown>
**Explicit lifecycle**

Schema changes are handled by Alembic instead of silently mutating the database during app startup.
</div>

<div class="fq-card" markdown>
**Dependency-aware health**

Liveness answers “is the process alive?” while readiness answers “can this instance serve traffic?”
</div>

<div class="fq-card" markdown>
**Immutable builds**

Frontend and API images are built as deployable artifacts and configuration comes from the environment.
</div>

<div class="fq-card" markdown>
**Safe state boundaries**

Study mastery is durable PostgreSQL state; XP/combo effects are intentionally ephemeral browser-session state.

## Liveness vs readiness

FlashQuest’s exposes three operational endpoints:

```text
GET /health
GET /health/live
GET /health/ready
```

### Liveness

`/health/live` confirms that the API process is responding and returns service metadata. It does **not** make PostgreSQL part of the liveness signal.

Why that matters: if the database has a temporary outage, killing and restarting otherwise-healthy API processes can amplify an incident rather than resolve it.

### Readiness

`/health/ready` executes a real database query. If PostgreSQL is unavailable, the endpoint returns HTTP `503`.

That makes readiness a traffic-routing decision: an API process can remain alive while being removed from service until its critical dependency is usable again.

Docker Compose uses this readiness endpoint before starting the web service.

---

## Request observability

Every HTTP response includes:

```text
X-Request-ID
X-Response-Time-Ms
```

- **`X-Request-ID`** is propagated from the caller when supplied, otherwise generated by the API.
- **`X-Response-Time-Ms`** exposes server-side request duration.

These are small building blocks, but they create a clear path toward structured logging, distributed tracing, and correlation across reverse proxies or downstream services.

!!! example "Troubleshooting with a known request ID"
    ```bash
    curl -i \
      -H 'X-Request-ID: interview-lab-042' \
      http://localhost:8080/health/live
    ```

## Configuration contract

Runtime behavior is environment-driven:

| Variable | Purpose |
| --- | --- |
| `DATABASE_URL` | PostgreSQL/SQLAlchemy connection string |
| `APP_ENV` | runtime environment label |
| `APP_VERSION` | version surfaced in service metadata |
| `LOG_LEVEL` | logging configuration input |
| `ALLOWED_ORIGINS` | JSON array or comma-separated browser origins |
| `VITE_API_URL` | API endpoint embedded into the frontend build |

No environment-specific credentials belong in Git.

A useful interview distinction here is **build-time vs runtime configuration**: Vite’s API URL is compiled into the static frontend artifact, while the FastAPI process reads server configuration at runtime.

## Database lifecycle

Alembic owns schema change.

On a fresh database:

```bash
docker compose exec api \
  alembic -c /app/alembic.ini upgrade head
```

Only after the schema exists should the curriculum be seeded:

```bash
docker compose exec api python -m app.seed
```

This makes schema mutation deliberate, reviewable, and testable independently of application startup.

CI proves the migration path against a **clean PostgreSQL 16 service**, which protects against the common “works on my existing database” failure mode.

## Curriculum as versioned environment data

The built-in curriculum lives outside application logic:

```text
backend/app/data/
├── platform_engineering_cards.json
└── platform_engineering_labs.json
```

The seed loader validates those files and inserts them idempotently.

This creates a useful separation:

- application code owns behavior;
- Alembic owns schema;
- JSON data owns the built-in learning environment;
- PostgreSQL owns durable user study state.

See the [Curriculum](CURRICULUM.md) and [Break/Fix Labs](LABS.md) pages for the study model.

## Container posture

The API container is deliberately hardened beyond a default development image:

- slim Python runtime;
- only required OS packages;
- unprivileged application user;
- readiness-backed Docker health check;
- application configuration passed through environment variables.

The frontend uses a multi-stage Node build and serves the final static assets with Nginx.

Why this matters for Platform Engineering: the runtime image should contain what is needed to **run** the application, not the full build toolchain.

---

## Dependency-aware startup

Compose models dependency health rather than only startup order:

```text
PostgreSQL healthy
      ↓
FastAPI starts
      ↓
API readiness passes
      ↓
Web starts
```

This still is not a replacement for application retry/backoff — real distributed systems must tolerate dependencies becoming unavailable **after** startup — but it makes the local environment deterministic and demonstrates the difference between “container exists” and “dependency is ready.”

## CI quality gates

The pull-request pipeline is deliberately read-only: it validates code rather than modifying and pushing contributor branches.

### Backend matrix

Python 3.11 and 3.12 run:

- compilation;
- pytest;
- Ruff correctness checks;
- Black formatting checks.

### Frontend

The frontend runs:

- clean `npm ci`;
- ESLint;
- TypeScript/Vite production build.

### Database

A clean PostgreSQL 16 service receives:

```text
alembic upgrade head
```

### Containers

CI validates:

```text
docker compose config
API image build
web image build
```

### Documentation

MkDocs + TypeDoc run separately so documentation has an independent failure boundary while still being validated before merge.

## Failure boundaries

| Boundary | Example failure | Intended signal |
| --- | --- | --- |
| API process | crash/import failure | liveness / container state |
| PostgreSQL dependency | unavailable DB | readiness `503` |
| Schema | bad migration | CI migration smoke test |
| Frontend | type/build regression | frontend CI |
| Container packaging | broken Dockerfile/Compose | container build job |
| Docs | broken nav/import/reference | strict docs build |
| Curriculum | duplicate/wrong deck shape | seed regression tests |

This makes failures easier to classify instead of collapsing everything into “the app is down.”

---

## Durable vs ephemeral state

FlashQuest’s intentionally keeps two categories of state separate.

### Durable

Stored in PostgreSQL:

- cards;
- mastery/bin state;
- review timing;
- wrong counts;
- review history.

### Ephemeral

Stored in browser session state:

- current session XP;
- combo count;
- session accuracy presentation.

That means playful UI feedback can evolve without becoming the source of truth for learning progress.

## Platform interview talking points

FlashQuest’s gives you concrete implementation examples for questions such as:

- What is the difference between liveness and readiness?
- Why should schema migration be separate from application startup?
- Why run containers as non-root?
- How do you make CI a quality gate instead of a code-mutating workflow?
- What is the difference between build-time and runtime configuration?
- How do request IDs help during distributed troubleshooting?
- Why validate migrations against a fresh database?
- What state belongs in PostgreSQL versus the browser?
- How would you extend this architecture with Kubernetes, OpenTelemetry, or an artifact registry?

!!! note "Good portfolio framing"
    Describe FlashQuest’s as a **small, production-minded platform demo**, not as proof that you operated a large production fleet. The useful story is the engineering decisions, failure boundaries, automation, and tradeoffs.
